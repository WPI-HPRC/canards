# Canards flight software: test plan

2026-11-21. For the canards team: flight software, GNC, EE, and Nic (telemetry, SD logging).

This is the path from "builds and passes desktop tests" (where `mikayla` stands today) to "ready to fly", and then through the flight itself. Each step says what to do, what passing looks like, and what to write down. **Stop at the first step that fails,** fix it, and redo that step before moving on. Later steps rely on the earlier ones.

Owners: **FSW** flight software, **GNC** guidance and control, **EE** board and wiring, **Nic** telemetry and SD.

---

## 0. Reading the telemetry

Every bench step reads the telemetry, so this section comes first. The same columns go over the radio and over USB.

- Over USB: `python3 ground/telemetry_gui.py --usb --flight`
- Over the radio: `python3 ground/telemetry_gui.py --flight`

| Column | Meaning |
|---|---|
| `state` | 0 Init, 1 PreFlight, 2 Boost, 3 Control, 4 Coast, 5 Chute, 6 Land |
| `mode` | canards: 0 Off (unpowered), 1 Neutral (powered at 0°), 2 Controlling, 3 Testing |
| `enabled`, `locked`, `cutoff` | control enabled; lock-out (a launch that skipped PreFlight); envelope cut-off latched |
| `act_test` | 1 while the actuator sweep runs |
| `sensor_ok` | bits: 1 IMU, 2 magnetometer, 4 barometer, 8 SD log. **15 = all OK** |
| `nav_ok` | bits: 1 IMU, 2 attitude, 4 speed, 8 altitude. In Init only bit 1 is set (1). After arming and alignment, all four (15) |
| `gates` | why attitude hold is blocked: 1 not enabled, 2 locked out, 4 safety fault, 8 nav invalid, 16 speed low, 32 cut-off, 64 controller failed, 128 non-finite |
| `safety` | sticky faults since boot: 1 IMU gap, 2 time backwards, 4 IMU read failed, 8 IMU non-finite, 16 transition refused. **Should stay 0** |
| `speed`, `alt_m`, `tilt_deg` | estimator: inertial speed, altitude above the pad, angle from vertical |
| `sf_g`, `fx_g`/`fy_g`/`fz_g` | accel magnitude, and accel along body x (nose), y and z, in g |
| `p_dps`/`q_dps`/`r_dps` | body rates: roll about the nose, pitch, yaw |
| `cyc_max_us`, `gap_max_us` | longest cycle and longest gap between IMU samples, over the last second |
| `imu_missed` | IMU samples the loop was too late to read, since boot |
| `log_rows`, `log_drop` | SD log rows written; rows dropped because the SD card fell behind |
| `sim_mode` | 0 flight, 1 SD replay, 2 USB stream |

Body axes: **x is out of the nose.** Positive roll (`p_dps` > 0) is clockwise as seen from the tail. A positive canard angle also means clockwise seen from the tail: the leading edge turns clockwise.

## Phase 2: Bench session 1, over USB with no radio

Setup:
- The board is on the airframe with the canards fitted.
- Servo power is connected, and USB goes to a laptop.
- The laptop runs `python3 ground/telemetry_gui.py --usb --flight` (requirements: `pip install -r ground/requirements.txt -r tools/requirements.txt`).

Safety:
- **The servos power up and drive to 0° at boot. Keep your fingers clear.**
- Once you send `armFlight`, launch detection is live (5 g held for 50 ms). Don't drop or bang the board. If a launch is ever detected on the bench, power-cycle.

### 2.1 Flash and boot

Flash with `pio run -e marsv21 -t upload`, then connect the GUI.

| Check | Pass |
|---|---|
| Canards at power-up | move to 0° and hold (this also checks the PA4 servo power and the PB12 level shifter) |
| `state`, `mode`, `sim_mode` | 0, 1, 0 |
| `sensor_ok` | 15 |
| `log_rows` | climbing, about 208 per second |
| `safety` | 0 |

If a USB host has the port open while the board boots, the board waits 1.5 s for a mode line before starting. That is expected.

### 2.2 Loop timing (this settles the 208 Hz question)

Leave it running for 5 minutes untouched.

| Check | Pass | Write down |
|---|---|---|
| `gap_max_us` | steady at about 4800, never near 25000 (above 25000 counts as an IMU-gap fault) | typical and worst |
| `cyc_max_us` | well under 4800 | typical and worst |
| `imu_missed` | stays 0 | final value |
| `log_drop` | stays 0 | final value |

Write down `log_rows` per minute: rows are about 340 bytes each, so the log grows by roughly 4 MB a minute. If samples are missed or log rows dropped, stop: GNC and FSW decide the IMU rate before going on, and GNC regenerates the gains for that rate.

### 2.3 Canard sweep: which canard is which, and which way it moves

Film the canards from the tail and click **Actuator test**, or type `actuatorTest` in a serial terminal. The board must be in Init.

- The sweep moves canards 0 to 3 one at a time, each to +5° then −5°, then all four +5° and all four −5°. Each step lasts 300 ms; the whole sweep takes 3 s.
- `mode` reads 3 and `act_test` reads 1 during the sweep. Both return to 1 and 0 afterwards, with the canards at 0°.

| Check | Pass | If it fails |
|---|---|---|
| Order | each canard is a quarter turn clockwise (seen from the tail) from the one before: CH1, CH3, CH4, CH2 | `channelOfCanard` in `include/VehicleConfig.h` is wrong |
| Direction | each +5° step turns the leading edge **clockwise** seen from the tail | set that canard's `canardSign` to −1 |
| Size | about 5°, the same on every canard (use an angle gauge if you have one) | redo that channel's calibration in Canards-Rocket `canard_bench` (`cal N`) |

Record the results per canard. Then download the log (2.8). The log holds each cycle's command (`cmd0..3`) and encoder reading (`enc0..3`), so GNC can measure the real servo lag from the sweep steps; the gains assume 30 ms (`servoModelTauS`).

### 2.4 IMU orientation (the mount map)

In Init, hold the rocket still in each position and read `fx_g`, `fy_g` and `fz_g`. The accelerometer reads +1 g on whichever axis points **up**.

| Position | Pass |
|---|---|
| Nose up | `fx_g` ≈ +1.00, the others ≈ 0 |
| Lying on its side, CH1 canard pointing up | `fy_g` ≈ +1.00 (CH1 sits on body +y) |
| Lying on its side, CH3 canard pointing up | `fz_g` ≈ +1.00 (CH3 sits on body +z) |

Then turn it by hand:

| Motion | Pass |
|---|---|
| Spin the rocket about its nose, **clockwise seen from the tail** | `p_dps` > 0 |
| Tip the nose toward CH3 | `q_dps` < 0. With x out of the nose, a rotation that tips the nose toward +z is a negative turn about +y |
| Tip the nose toward CH1 | `r_dps` > 0 |

Any axis that fails means `kImuToBody` in `include/VehicleConfig.h` is wrong. That would also flip the control direction, so fix it before anything else. Canards-Rocket measured this map on 2026-11-20; this step confirms it on the flight code.

### 2.5 Arming and the estimator on the pad

Put the rocket nose up and still, and click **Arm flight** (or type `armFlight`).

| Check | Pass | Write down |
|---|---|---|
| `state` | 1 (PreFlight), `enabled` = 1 | |
| `nav_ok` | 15 within about a second (alignment collects 128 still gyro samples, about 0.6 s) | time to 15 |
| `tilt_deg` | about 0, and follows when the rocket is tilted by hand | |
| Canards | stay at 0°; `mode` = 1 (attitude hold runs only in Control) | |
| Drift | leave it 5 minutes: `tilt_deg`, `speed` and `alt_m` stay near 0 | drift after 1, 2 and 5 minutes |

This estimator is gyro-only after alignment, so its attitude drifts for as long as the rocket waits in PreFlight. Use the measured drift to decide how long before launch to send `armFlight`, and pass it to the estimator owner.

After arming, the watchdog is running and log download is refused until a power-cycle. Power-cycle before the next step.

### 2.6 Control direction: the whole chain, on the real servos

This is the most important bench check: if the sign is wrong anywhere, the canards make a roll worse instead of fixing it. It is the only bench test that drives the board into Control, because the Control state needs flight speeds.

```bash
python3 tools/usb_stream.py stream --synthetic --roll-rate 20 --servos -o sign.csv
```

The board runs a generated flight through its real estimator and controller. During burn and coast the flight rolls clockwise (seen from the tail) at 20 °/s.

| Check | Pass |
|---|---|
| States in `sign.csv` | the state sequence reaches 3 (Control) and continues to Coast, Chute and Land |
| Commands in Control | `cmd0..3` (radians) all **negative**, reaching about −0.070 (the −4° canard limit) |
| Canards (watch from the tail) | during the Control window, all four leading edges turn **anticlockwise** together, against the roll |
| Chute | servo power drops (`servo_power` = 0) |

Repeat with `--roll-rate -20`: the commands should be positive and the canards should turn clockwise.

If the board never reaches Control, tell FSW. The synthetic flight has only ever run against a scripted estimator, never this one.

Steps 2.3, 2.4 and 2.6 together cover every link from the gyro to the canard:
- 2.4 checks the sensor and its mount.
- 2.6 checks the controller, the mixer and the servos.
- 2.3 checks the servos one canard at a time.

### 2.7 Synthetic flight with no roll

```bash
python3 tools/usb_stream.py stream --synthetic -o synth.csv
python3 tools/flight_log.py summary synth.csv
```

**Pass:** the states arrive in order: Init, PreFlight, Boost, Control, Coast, Chute, Land. Canard modes follow: Neutral, Controlling in Control, Neutral, then Off from Chute. `safety` stays 0. Keep `synth.csv` as the board's reference result.

### 2.8 Log download and replay on the board

1. Boot, record about a minute (move the rocket around, run one sweep), then power-cycle.
2. `pio run -e marsv21 -t dumplog` (the previous boot's log), then `python3 tools/flight_log.py summary <file>`.
3. `python3 tools/usb_stream.py replay <N>`. The banner names the new log number. Wait for `# replay done`.
4. Power-cycle, download both logs, then `python3 tools/flight_log.py compare A.csv B.csv`.

**Pass:** the summary matches what you did, and `compare` reports **no differences**. Write down how long the download took and how fast the replay ran.

### 2.9 Failure behaviour

| Do | Pass |
|---|---|
| Unplug USB in the middle of a session, then plug it back in | the board never resets or stalls (`gap_max_us` stays normal); the GUI gets the header again on reconnect |
| Open a serial terminal and stop reading from it for a minute | no stall; telemetry rows are skipped on USB only |
| Boot with no SD card | `sensor_ok` = 7, the board still runs, telemetry works |
| Tap the airframe firmly while armed (on foam, by hand) | no launch detection (`state` stays 1) |
| Type `dump` after arming | refused with an ERROR message, no reset |

## Phase 6: Flight readiness

All of the following must be true:
- [ ] Phases 1 to 5 passed on the **exact** commit being flown, and that commit is written down.
- [ ] No `PLACEHOLDER` lines left, or each remaining one is accepted in writing by its owner.
- [ ] 2.3, 2.4 and 2.6 passed after the last time anything was taken apart (the canard zero angles were set by hand).
- [ ] The SD card has been emptied: log numbers wrap at 100 and old files are overwritten without warning.
- [ ] Decided whether the first flight is **active** (canards controlling) or **passive** (canards held at 0°, logging only). A passive flight needs a new `armPassive` command, which is PreFlight without enable; FSW can add it. It gives real flight data to replay through the controller before trusting it.

## Phase 8: Flight and after

**On the pad:** follow the Phase 5 checklist. Watch `state`, `nav_ok`, `gates`, `safety` and `tilt_deg` up to launch.

**After recovery:**
1. Power on in Init. **Do not arm.**
2. Run `dumplog`, then `flight_log.py summary`.
3. Replay the flight log on the board (2.8) and run `compare`: no differences means the code flown is the code under test.
4. GNC compares the flight with the sim, especially roll rate against canard commands during Control, and the servo lag.
5. Write down what went wrong and what changed before the next flight.
